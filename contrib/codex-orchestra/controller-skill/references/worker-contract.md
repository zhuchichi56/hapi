# 工作者契约

每个派出的任务书都带这份契约。工作者只对**后台收件**负责,不找总控聊天、不找用户。

## 一、任务书必含

1. **三句开头**:要得到什么、保留什么 / 先解决哪个具体缺口及原因 / 交什么可见结果才算完成。
2. 验收标准(逐条可检验)、文件所有权(`ownership`,写绝对路径或分支)、授权范围、禁止项、检查点。
3. **截止**:每个工作聊天最多 2 小时;超时保留已完成项与接手入口,不写完成,不自动延期,不连带停止远端任务。
4. **只在四个时刻回执**:完成、受阻、要输入、失败。**不汇报进展**(进展由代码层读取)。
5. 不独占代码库:保留并行修改;共享文件只有指定写者可改。

## 二、回执五项(每次 ≤100 字正文,其余放文件)

| 项 | 写什么 | 对应回执 JSON 字段 |
|---|---|---|
| 结论 | 做完没有:是 / 否 / 部分 | `summary` 开头 |
| 成果 | 1 个链接或路径 + 1 张图或 1 个例子 | `summary`(合计 ≤500 字) |
| 自验 | 逐项:通过 / 未通过 / 未验证 + 证据路径。**不以打勾代替测试** | `checklist` |
| 剩余 | 没做的、已知风险、接手方式 | `limitations` |
| 需要 | 无;或 1 个具体问题 + 推荐 | `kind=need-input`(有问题时) |

`kind`:`delivery`(完成/阶段交付)· `blocked`(受阻)· `failed`(失败)· `need-input`(要输入)。**完成**之外的三类默认按 P0 处理(SKILL §四)。

## 三、提交

写 JSON 后入账(不要往总控聊天发消息):

```json
{
  "eventId": "T022-delivery-20261103-1",
  "taskId": "T022",
  "sessionId": "<账本里的 session 标识>",
  "turnId": "<本回合 turn id>",
  "kind": "delivery",
  "occurredAt": "2026-11-03T08:00:00+00:00",
  "summary": "结论:是。成果:<链接>;示例:<一句>",
  "checklist": ["需求A:通过(证据路径)", "需求B:未验证(原因)"],
  "limitations": ["剩余:...;接手:..."],
  "source": "<执行器标识,如 codex-cli>"
}
```

```bash
codex-orchestra receipt-enqueue --json receipt.json
```

`eventId` 稳定唯一,重试不换。DSH/CLI 执行者没有 App 工具,用上面的持久入口,不得假装能直接发聊天消息。

## 四、不要做

- 不汇报"正在做什么"。**误发的进展消息**:公开进展由 collector 只读采集,不作为业务回执,不建待决项,不触发模型;重复发生时,项目审查(或 Root)在下一次交互里用一句话提醒本契约即可,不专门起一轮。
- 不把中间文件、测试日志堆进回执;路径放 `limitations` 或 `checklist`。
- 不替用户做 D2 决定(见 [放权清单](delegation.md) B 栏)。
- 不自验自归档;归档由用户确认后总控触发。
