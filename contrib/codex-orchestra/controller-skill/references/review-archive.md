# 验收、返工、归档

## 1. 收到什么、怎么看

回执只走后台收件与 collector;**禁止**用 `send_message_to_thread`、native wake 或回执 marker 把回执发到总控聊天(安装策略 `receipt_native_wake_enabled` 默认 OFF,不得为巡检或测试重新打开)。保留收件、去重、ACK 与 pending/unknown 记录。

```bash
codex-orchestra consume     # 未确认的 delivery/blocked 回报,读取不删除
codex-orchestra snapshot
```

先对照合同检查真实产物与关键验证;模型最终答复不等于验收。必要时一次 `read_thread` 或 `wait_threads(timeoutMs:0)` 核对,不全量反复读取。一个失败或慢的聊天不阻塞其他任务。采集断开/过期不自动认定失败,也不当作完成。

## 2. 验收三级

1. **确定性核验**(代码):文件存在、测试通过、哈希一致、产物可打开。
2. **语义审查**(一次性审查运行或内部 Sub Agent):对照验收标准找缺口;**每次验收决定必须写 `evidence_ref`**(指向已核对的证据),缺证据只能返工或 hold,不能 accepted;交"可通过范围、具体缺陷与证据、未验证项、建议",不能以"子 Agent 通过"直接替代结果。普通检查先用脚本,只有需要判断的才交审查。
3. **Root 终审**:只看用户可见的成果,亲自核对关键数字。

收到回执先持久化并去重,再核对产物,然后作出明确决定:验收 / 具体返工 / 范围内排障或换路径 / 等待真实依赖 / 向用户提具体问题。ACK(确认收到)与业务验收分开;失败时保留未决,不能先 ACK 后丢失下一步。每个真正需要判断的事项有稳定 `decisionId`,关联 task/session/turn/receipt,记录触发、选项、决定、理由、时间、下一步责任人;重复回执不重复计数。

### 两个常见情形(照此处理)

- **回执 `summary` 写"是",但 `checklist` 有未通过/未验证项** → 不整体验收。核对证据,回原聊天只提**一个**具体缺口和下一步;不找用户。阶段性成果只在合同范围内单独验收。
- **聊天原生状态 `interrupted`,且合同要求的产物不存在** → 先标该事实"未知",读一次原生状态并核产物;确认缺件后 `rejected` 并回原聊天补交,记一条 decision。属于授权内可恢复、不影响承诺的,**静默**处理(判据见 SKILL §四)。

## 3. 命令

- 通过:`review T009 --result accepted --op-id t009-review-1 --evidence '实际核对的文件与验证'`
- 未通过:`review T009 --result rejected --op-id t009-review-1 --evidence '具体差距'`;在授权覆盖的目标聊天用 `send_message_to_thread` 安排返工(这是给工作聊天的指令,不是回执)。新 completed 回合再次进入待验收,旧回调不抹掉判断。
- 处理完具体回报才 `ack NOTICE_ID`。操作 ID 稳定、唯一;同一次未知副作用不换 ID 重发。
- 多 Session:`session-review TASK --session-id ID --result accepted --evidence TEXT --op-id ID`;`end-session` 只结束本地职责记录,不原生归档。整任务验收或归档要求所有附属职责都已结束。
- 简报:`brief TASK --text '结论一句。数字或下一步一句。' --as-of ISO`(≤2 句、≤80 字,写法与坏例子见 [界面与汇报偏好](ui-and-reporting.md);与原生 progress 分开存,采集不覆盖,不调用模型)。成果:`prepare-artifact TASK --index 0` 准备已登记报告供网页读取,原文件变化后须重新准备。

## 4. 归档

- 只归档本总控登记、已验收的工作聊天,且满足下列之一:① **用户对本次明确确认**;② 用户已按类别明确放权(见 [放权清单](delegation.md))且该聊天在登记范围内、所有附属职责已结束。总控永久保护;活动、待返工、待用户决定和外部旧聊天不归档。实施聊天不能自验自归档。
- 验收通过且取得用户确认后:`archive-request T009 --op-id t009-archive-1`。daemon 会先核对原生归档身份,再经现有 Native Desktop 调用原 App 归档,无需再发一次归档工具。
- 归档是独立状态:unknown 只对账、不重放;明确未发送/拒绝最多三次退避,仍失败则保留"已验收、归档待处理"。主动对账用 `archive-run`;人工完成后用 `archive-receipt T009 --op-id ... --result confirmed --evidence '原 App 归档回执或列表核对'` 登记。不把"请求已发出"当成功。
- 多个待归档任务合并成**一条**问用户(SKILL §三 D2)。

## 5. 结论怎么说

对用户的每项状态以可理解的结论开头:做完没有、得到什么结果、是否还需处理。不能只写"报告已交/待总控验收"。历史观测带时间,不冒充当前状态。只读调查明确"未知"但满足调查合同,可验收为"调查完成",不包装成已修复或全部正常。不把"待总控验收"长期摆给用户当行动项:能验收的立即验收,有缺项就定位并找原负责人纠偏。

每项工作结束,在任务总控原有成果入口给一份简短交付报告:**要求什么 → 实际做了什么、做完没有 → 一张图/一个例子/结果链接 → 验收结论**。缺项具体写出,少内部术语。
