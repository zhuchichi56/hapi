# HAPI Desktop：对话整理与性能基线

2026-11-01，由当前主会话直接实施。已交付可重复运行的只读 benchmark、完整本地元数据清单、三条原生归档回执，以及一处实测有效的历史读取改进。整体性能门禁仍为失败：公网直连和未打开会话的模型设置等待尚未解决。

## 对话盘点与归档

原 Codex 元数据库共2,004条记录，Claude原桌面会话32条，共2,036条。这个数字包含CLI、子Agent、后台评审及历史HAPI来源，不能称为2,036个桌面主对话。归档前，按原生来源与thread_source筛选的未归档桌面主对话为344条；归档后341条（Codex313、Claude28）。已归档记录始终保留。

已通过原App归档两个已完成的Codex「HAPI 桌面原会话验收」和一个已确认idle的Claude同名验收会话，原生元数据独立确认三条变更。保留图片验收会话用于后续benchmark。没有按“标题重复”“很久没用”或notLoaded批量推断任务完成，也没有清理运行/置顶/用途不明的会话。普通ChatGPT聊天不在当前两种桌面适配器的范围内。

私有产物在x20 `work/native-benchmark-20261101/`：`inventory-before.json`、`inventory-after.json`、`conversations.html`（本地搜索、来源/归档过滤、原App链接）、`archive-receipt.json`。实际浏览器确认默认341条主对话，按图片验收标题搜索精确匹配一条。原App归档动作通过原工具/适配器完成，清单脚本只读；私有标题和会话ID不提交Git。

API每条路由内部串行，最多四条路由同时测；正式基线每个历史/增量场景各五次。列表、设置、目录和可用的更早消息/详情各一次，属于冷诊断，不作三次相对性能结论。只读白名单排除发送、停止、归档、置顶、模型修改和审批提交。凭据仅在内存；输出不保存正文、工具输出、原始错误或认证响应。原生请求不启动模型生成。

基线门槛预先设为本机300ms、Mini1000ms、公网5000ms，浏览器原消息首屏≤5秒、CLS≤0.1、零错误/横向溢出及串行完成的轮询。API相对比较要求至少三次、同配置/协议/原历史指纹，中位数同时超过20%与50ms才标记回归。不可比较、遗留失败与新增回归分别报告。五次样本的nearest-rank p95就是最大值，不能代替长期可靠性。

## 测得的瓶颈与本次改进

原生历史读取先等owner连接最多400ms，再检查原生fallback缓存。对已知没有live owner的历史，这段等待每次重来，连百字节unchanged响应和工具详情也受影响。现在已有成功fallback时，继续并行发现owner，直接检查live snapshot或读取原App历史；缓存TTL仍为1300ms，过期后仍调用原App，不新增缓存或服务。初次400ms grace保留。

同一冻结工具历史、同配置、原生指纹一致的结果：

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 本机增量读取中位数（各5次） | 401.856ms | 0.464ms |
| 本机增量读取p95（各5次） | 411.105ms | 1.412ms |
| 本机历史读取中位数（各5次） | 474.488ms | 0.633ms |
| Mini增量读取中位数（各5次） | 413.836ms | 4.390ms |
| 修改后本机首次fallback读取 | — | 455.025ms，仍超过300ms目标 |

补充用每次间隔1400ms、确保原1300ms缓存已过期的三次原App读取，得到108.635/55.567/55.668ms，均值73.290±30.610ms（样本标准差），原历史指纹一致。说明收益不只来自延长缓存；实际上没有改TTL。日常查看历史、展开工具和增量跟随位于交互关键路径，收益值得保留，累计调用频率和节省时间尚未知。

未打开的历史会话读取模型设置仍约5秒（本机5001ms，单次），来自原owner订阅/发现等待，本次没有修改这条设置确认链路。首次fallback的400ms也保留为明确未达标项。

## 公网与浏览器结果

API修改前：本机40/40、Mini原生40/40成功，现有代理原生40/40成功；公网直连认证失败。修改后：本机及Mini原生仍各40/40、代理40/40成功；直连29次总请求（含认证）16次失败，类型为URLError9、timeout5、ConnectionResetError2。没有已返回HTTP状态，不将这些失败误报成已证实的origin 502。

代理部分历史/增量的相对延迟仍触发回归门禁。跨时段公网波动、多个共享原生读者及同时浏览器测量不构成隔离因果试验，不能把这些差异解释为代码修复提高或降低公网速度。公网稳定性是下一优先项，继续保留红灯。

真实公网浏览器使用现有代理、同一图片验收对话，三次冷/暖缓存；弱网条件为200ms、512000Bps下载、256000Bps上传、4倍CPU降速：

| 场景 | 最终原消息首屏中位数 | 三次最大值 |
| --- | ---: | ---: |
| 正常冷缓存 | 3.202s | 3.324s |
| 正常暖缓存 | 2.273s | 3.432s |
| 弱网冷缓存 | 4.065s | 4.211s |
| 弱网暖缓存 | 2.344s | 3.090s |

最终浏览器12/12流程满足本次预算，相对比较通过；较早的弱网冷启动曾5.794秒超标，原始失败保留，不能据最后一批绿灯保证公网稳定。初批冷资产7个/519418传输字节，CLS最高0.0353，未观察到longtask。菜单两帧paint最终正常中位15.3–18.0ms、弱网22.7–24.9ms，单次最高80.8ms。这是实验室菜单响应，不是field INP或模型推理时间。

UI真实缩略图180×120px、加载成功；1440/390/320px均无横向溢出，模型面板完整处于视口内。60个合成滚动帧间隔p95=17.3ms、最大24.4ms，仅针对这条短图片验收聊天，不能外推长历史FPS。十秒idle轮询观察到三个原历史请求全部成功、最大在途1；它不认证active场景或断网恢复全过程。

## 按收益排序的后续清单

1. **公网直连稳定性**：已有真实失败。下一步从失败设备/路径取得同协议握手及请求证据；保留现有代理可用路径，不猜测改DNS、增加端口或重放写入。
2. **历史模型设置的被动等待**：本机约5秒。值得单独优化读取路径，保持真实原生设置及写入确认规则，不能用默认模型冒充回读。
3. **完整历史查找**：原`list_threads`接口最近50条普通聊天加置顶，没有普通历史cursor；前端搜索范围受该列表限制。完整清单证明历史仍存在。产品可按需补全局历史入口，避免每轮扫描原数据库。
4. **选择题覆盖**：Codex原生`item/tool/requestUserInput`已支持选项、补充答案、原question/request/owner提交及过期拒绝；已有前端与原生测试。特殊MCP/异步弹窗和纯正文选项不等于这条协议，尚未逐种实测。Claude只接Allow/Reject审批，尚未完整连接`AskUserQuestion`选择题；需要基于真实待答面板接原控件及原会话，不能把“回复1/2”冒充原按钮提交。
5. **暂缓外观改造**：本次小图、手机布局、模型面板边界和基础渲染通过。后续只依据真实问题改动，优先把新benchmark持续用于更新验收。
