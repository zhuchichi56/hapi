## 没有采纳的扩大修改

- **不把共用25秒总预算直接判成bug。** 晚到的首次失败留给重试的时间较少，是有意限制总等待的权衡；更换每次独立25秒会加长等待。真正该改的是新鲜度表达与分层诊断，超时阈值须用尾延迟证据决定，不立即缩到8秒。
- **不把ack后切换页面的等待气泡消失称为消息丢失。** 原App已确认接收；可以按会话保留等待记录，不能把已确认发送重新放回“未发送草稿”诱导重复提交。
- **不先优化未测量的微小成本。** 模型目录重复HTTP、长会话memo/JSON序列化和多标签轮询可后续测量；当前没有帧耗时证据，不据此重构。
- **Antigravity的部分静态判断未采纳。** Node `server.requestTimeout`约束请求接收，不等于收到完整请求后60秒终止adapter处理；浏览器写预算75秒略长于Hub60秒，本身是合理的外层预算。它所指的listen/chmod窗口在Mac的host socket，而Hub校验的是Mini的SSH转发socket，不能据此认定Hub会看到这个权限窗口。先前缓存失败结果和最多256条驻留也不是“无界缓存”。
- **不把探测超时当作socket已死。** Antigravity建议探测超时后resolve(false)，结合现有unlink会误删尚未证实死亡的宿主路径；不采纳。只能对明确stale错误做清理。
- **低优先级信息精度改善可保留。** Hub在stage=socket、尚未调用connect时仍返回delivery=unknown；可准确改为not-sent。当前保守值不会自动重放或丢写，因此不当作本次断连根因。
- **不新增会话数据库、定时监控或自动重发。** 原App仍是唯一会话来源。

## 方案判断与修复顺序

当前最划算的是保留原生桥接，依次处理：共享进程局部失败 → 当前聊天健康状态 → 工具详情保留 → 写入不确定性 → 接管和模型缓存恢复。每项用对应聚焦回归核验，再按既有部署流程上线，不能把本轮审计写成这些修复已经上线。

跨设备链路包含MacBook公网连接器、本地转发、Mini Hub、反向SSH、原生App。这些都是可用性依赖。Mini目前仍依赖MacBook提供外网，单把连接器搬过去不能消除断网单点。只有Mini有独立稳定网络后，才值得同条件比较入口迁移；MacBook及原App离线时，任何保留原会话控制的方案都无法继续实时操作。暂不为未经验证的收益重写成另一套WebSocket同步系统。
